# Подтверждённая почта — v0.6.8.1

Рабочая реализация поверх 0.6.8. Выпуск 0.6.8 уже опубликован; изменения этого документа ещё не означают публикацию 0.6.8.1 или применение миграции на рабочем сервере.

## Поведение

Новый аккаунт требует подтверждённую почту. Поле в интерфейсе не является единственной проверкой: сервер отклоняет создание аккаунта без действующего подтверждения, включая запрос старого клиента. Существующие аккаунты продолжают входить, читать и отправлять сообщения без почты. При запуске предлагается привязка с кнопкой «Позже»; заметное напоминание остаётся до привязки. По решению владельца подтверждение выполняется ссылкой, не цифровым кодом.

Адрес хранится отдельно от публичного профиля и не отдаётся другим пользователям. Он приводится к нижнему регистру; один подтверждённый адрес принадлежит одному аккаунту. Почта не меняет пароль, ключи, список устройств или защиту копии истории. Восстановление шифрованной истории по почте не добавлялось.

## Firebase и секреты

Письмо отправляет Firebase Authentication. Используется обычное подтверждение адреса; SMTP и вход по email-link не нужны. Сервер через официальный Firebase Admin Go SDK 4.22.0 (Apache-2.0) подготавливает внутреннюю сессию Firebase только для отправки письма. Пароль NeoChat, recovery code, ключи и сессия NeoChat в Firebase не передаются. Firebase получает адрес и видит служебную запись подтверждения.

Сервисному аккаунту необходим доступ к Firebase Authentication; JSON остаётся вне Git. Серверу нужны:

- `GOOGLE_APPLICATION_CREDENTIALS`: существующий путь к серверному ключу.
- `NEOCHAT_FIREBASE_API_KEY`: API key того же проекта; берётся из предоставленной Android-конфигурации, а не вставляется в исходники.
- `NEOCHAT_EMAIL_BASE_URL`: публичный HTTPS origin NeoChat, без данных из пользовательского запроса.

Email/Password в Firebase уже включён. Домен `r1270286.s2566.vm.mydomain.zone` добавлен в разрешённые домены возврата; прежние домены сохранены. Это не включает почту автоматически в работающем NeoChat: отдельно нужны новый сервер, миграция и переменные процесса.

Android-конфигурация для релизных CI-сборок передаётся секретом `GOOGLE_SERVICES_JSON`. При его отсутствии релизная сборка завершается ошибкой, чтобы не опубликовать APK с неработающим push.

## Протокол

- `POST /v1/accounts/email`: начать подтверждение для нового аккаунта.
- `POST /v1/accounts/email/status`: узнать состояние по приватному `ticket` приложения.
- `POST /v1/accounts/current/email`: начать привязку для текущего пользователя и устройства.
- `GET /v1/accounts/current/email`: приватный адрес и состояние текущего аккаунта.
- `GET /v1/accounts/email/confirm`: страница подтверждения; открытие ссылки само по себе не меняет привязку.
- `POST /v1/accounts/email/confirm`: явное подтверждение получателем письма.
- `POST /v1/accounts`: принимает `email_ticket`; расходует подтверждение атомарно с созданием аккаунта.

Приложение и письмо получают разные случайные секреты; в БД лежат только их SHA-256. Секрет письма не возвращается приложению, поэтому знание адреса или уже установленный флаг Firebase `emailVerified` не подтверждает владение почтой. Результат привязки не зависит от присланного клиентом `user_id`. Устройство, запросившее привязку, повторно проверяется на отзыв при подтверждении.

Срок ссылки — 30 минут, повторная отправка — через минуту; лимиты также применяются по адресу и IP. Ограничения по адресу записаны в PostgreSQL и сохраняются после перезапуска. При ошибке отправки пригодного подтверждения не остаётся. Два параллельных запроса не могут создать два аккаунта по одному ticket. Откат регистрации, например при занятом нике, не расходует подтверждение. Почта и подтверждение обновляются с ограничением целостности БД.

Страница не загружает внешние ресурсы, использует `no-store`, `no-referrer` и CSP. В журналы идут шаблоны маршрутов, без query string, адресов, Firebase-токенов и ссылок подтверждения. После перехода из письма Firebase нужно нажать «Продолжить», затем подтвердить привязку на странице NeoChat и вернуться в приложение.

## Android: без постоянной службы по умолчанию

После успешного `set_push_token` сохраняется готовность push. При отсутствии явного пользовательского выбора `RealtimeService` выключается и постоянное уведомление исчезает. Явно выбранный резервный режим сохраняется. До успешной регистрации push резервное соединение остаётся включено по умолчанию, включая устройства без работающих Google Play services. В настройках режим называется «Резервное соединение в фоне». Периодическая синхронизация остаётся запасным путём.

## Проверки

Серверные тесты используют только отдельную удаляемую БД `NEOCHAT_TEST_DATABASE_URL`. Проверены неподтверждённый и повторный ticket, обязательность почты, разделение секрета письма и приложения, GET без мутации, отзыв устройства, лимит повторов, ошибка отправки, параллельное использование ticket, доступ существующего аккаунта без почты и отсутствие адреса в публичном профиле.

`TestNativeEmailFlow` запускает настоящий API с тестовым почтовым ящиком, который принимает только `@example.test` и имитирует переход получателя по ссылке. Этот код существует только в `*_test.go`, не в серверном или клиентском релизном бинарнике. E2EE, хранилище, авторизация, HTTP и одноразовые подтверждения остаются настоящими. Команда native-клиента передаётся JSON-массивом через `NEOCHAT_NATIVE_TEST_COMMAND`.

ПК: существующий `scripts/uitest.sh` теперь использует этот API; регистрация проходит форму подтверждения почты. Android: `scripts/android-email-test.ps1` предназначен только для тестового эмулятора, пробрасывает локальный API и убирает проброс после теста. iOS UI suite использует локальный API и PostgreSQL на macOS runner; Debug-приложение принимает тестовый сервер через launch environment, Release — нет.

Реальная доставка Firebase требует отдельного теста с почтой владельца. Проверка тестового ящика не считается проверкой фактического получения письма.
