# Бюджеты ресурсов и методика

Все числа ниже — **предварительные инженерные цели, не результаты замеров и не обещание ёмкости имеющегося VPS**. На M0 измеряется пустой клиент с криптобиблиотекой; после этого бюджет уточняется осознанно.

## Desktop

- Windows 11 x64, reference: Intel i5 8-го поколения, SSD, 8 GiB RAM, 1920×1080, Release без debugger.
- Private working set: ≤ 90 MiB в покое; ≤ 160 MiB при просмотре текстового чата с локальными 10 000 сообщениями и ограниченным окном загруженных строк.
- Cold start до доступного ввода: p95 ≤ 1.5 с, отдельно от догоняющего sync.
- CPU в покое: среднее ≤ 0.5% за 5 минут на reference-машине; без polling-таймера на каждый чат.
- Сжатая поставка со всеми Qt/crypto/SQLCipher DLL ≤ 70 MiB; установленный runtime ≤ 160 MiB. Отдельный application.exe не является размером продукта.

## Android и iOS

- Android reference: физический arm64 телефон с 4 GiB RAM, Android 12; iOS reference: iPhone 11, версия iOS фиксируется в отчёте.
- Android total PSS в покое ≤ 90 MiB, при открытом текстовом таймлайне ≤ 150 MiB. Не сравнивать PSS напрямую с desktop working set.
- iOS physical footprint ≤ 90 MiB в покое, ≤ 150 MiB на текстовом таймлайне; сжатая arm64 IPA ≤ 40 MiB.
- Android arm64 release APK ≤ 30 MiB. Debug, universal APK, dSYM и symbol files измеряются отдельно и не подменяют release-числа.
- Cold start до ввода: p95 ≤ 1.5 с на reference-устройствах, без ожидания сети.
- Фоновая работа: системный push вместо постоянного собственного socket; отсутствие необоснованных wake locks и периодических запросов каждые несколько секунд.

Android-дизайн v0.4 использует «жидкое стекло». До утверждения нативной реализации измерить прокрутку, frame time, PSS и энергопотребление со стеклом и с плотной заливкой на одном reference-устройстве. Размытие ограничить шапкой, композером и небольшими поверхностями; на основном экране не больше трёх одновременно. Не размывать каждый пузырь сообщения, не анимировать радиус blur, не добавлять постоянно движущийся фон. Под модальным окном использовать неподвижный фон. Если эффект недоступен, отключён системой или не укладывается в бюджет, использовать плотный тонированный материал с сохранением читаемости и управления. HTML-снимки не являются результатами этих замеров.

## Веб

Предварительные цели, не результаты измерений: первый UI JavaScript + CSS ≤ 150 KiB gzip без криптобиблиотеки и тестовых данных; полный лимит с crypto/WASM утверждается на M0 до выбора зависимости. В отчёте показывать оба размера, не скрывать криптографию из общего результата. При 10 000 локальных сообщениях — ограниченное окно DOM, целевой JS heap ≤ 40 MiB; учитывать отдельно память renderer, worker и декодированных вложений.

Reference: Windows 11, 8 GiB RAM, актуальный Chromium; точная версия фиксируется в отчёте, затем отдельные проверки Firefox/Safari. На широком экране не больше пяти основных blur-поверхностей: поиск, выбранный чат, нижняя навигация, шапка, композер. При превышении времени кадра использовать плотную заливку; сообщения не получают blur на каждый пузырь. Показать разницу с эффектом и без него, нажатия и прокрутку, после чего выбрать окончательный бюджет. До кода эти показатели не считаются достигнутыми.

## Сервер

Reference, который ещё предстоит выделить: Linux, 2 vCPU, 2 GiB RAM, SSD, один Go-процесс и PostgreSQL. Перед benchmark фиксируются CPU, лимиты systemd, версия БД и storage.

- Go RSS в покое ≤ 64 MiB; при 1 000 idle WSS-соединений ≤ 192 MiB. PostgreSQL, reverse proxy и файловый кэш измеряются отдельно; общий steady-state RSS служб целевой ≤ 768 MiB.
- Login/hash benchmark отдельный: два Argon2id worker по 64 MiB добавляют до 128 MiB RAM. Пиковый auth и рабочий messaging-трафик проверяются вместе; steady-state бюджет не маскирует этот пик.
- Установившаяся нагрузка: 20 логических send/с, 80% direct и 20% групповых, группы 16×3 устройств, fanout включён. Send ACK p95 ≤ 200 мс при RTT клиента к серверу ≤ 50 мс.
- Доставка foreground Qt → Android p95 ≤ 700 мс в той же сети, включая шифрование, HTTP send, WS-подсказку, sync и локальный commit. Доставка APNs/FCM измеряется отдельно и не входит в эту гарантию.
- Файл 25 MiB не добавляет 25 MiB RAM на каждый upload/download; целевой буфер ≤ 256 KiB на поток без учёта TLS/библиотечных буферов.

## Ограничение роста

Таймлайн запрашивает страницы по 100 сообщений и удерживает ограниченное окно, изображения декодируются под размер показа, thumbnail-cache ограничен байтами. Outbox, WS-очередь, HTTP body и фоновые задачи имеют лимиты и backpressure.

При 16 участниках с 3 устройствами pairwise fanout увеличивает ciphertext-хранение до 47 копий логического payload. Поэтому 30-дневное серверное хранение и upload-квоты важнее размера Go binary. До load-test нужно рассчитать диск по фактической длине ciphertext и интенсивности переписки.

Цели восстановления: **RPO ≤ 15 минут**, **RTO ≤ 2 часа**. Это требует проверенного backup/WAL-архивирования и внешнего хранилища, а не одного ночного snapshot. Потеря данных в пределах RPO при disaster restore возможна; обычный restart с исправным диском не должен терять committed ACK.

## Как измерять

1. Зафиксировать commit, конфигурацию Release, ОС, CPU, RAM, версии Qt/Go/crypto и сетевой RTT.
2. Выполнить 20 cold starts и измерить p50/p95; warm start отдельно. Если инструменты/сценарий меняют дисковый кэш, описать это явно.
3. Для памяти: 60 с после запуска, 5 минут покоя, затем 10 000 локальных сообщений с прокруткой и отдельный тест с изображениями. Приложить абсолютные значения и инструмент.
4. На сервере: 5 минут прогрева и 15 минут нагрузки, ACK/delivery p50/p95/p99, ошибки, RSS всех служб, CPU, disk I/O и размер БД/WAL.
5. Повторить 1 000 соединений, full-group fanout, burst login и обрыв сети у медленного клиента. Это тестовые сценарии, не фоновая нагрузка на рабочий VPS.
6. После значимого изменения зависимости, кэша, сериализации или криптографии повторить затронутый benchmark. Отчёт хранить с версией, а не править старые измерения.

## Если цель не достигнута

Сначала измерить вклад Qt-модулей, crypto bridge, расшифрованных изображений и кэшей. Убирать ненужные модули и лишние копии данных. Не ослаблять E2EE, ACL или проверку сертификата ради экономии. Если стоимость выбранной безопасной библиотеки превышает бюджет, показать измерение и изменить библиотеку/бюджет явным проектным решением.
