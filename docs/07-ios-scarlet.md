# iOS, IPA и Scarlet

## Решение

Нативный клиент на Swift/UIKit; обычный iOS-проект с выпуском IPA. Scarlet используется как канал установки/подписи. Не требуется jailbreak и не предполагается обход проверки сертификатов Apple.

Для сборки и диагностики iOS нужен macOS с Xcode: отдельный Mac или macOS runner. Текущий Windows-компьютер не считается подтверждённой iOS build-средой. Доступность Mac, iPhone и собственного signing profile пока неизвестна; проектирование и сервер от этого не останавливаются.

## Что установка не гарантирует

Документация Scarlet описывает разные способы установки, включая собственный сертификат. Доступность direct install зависит от статуса подписи. Поэтому «IPA установилась» и «приложение получает push после блокировки экрана» — разные результаты проверки.

APNs требует корректный App ID, разрешение push в provisioning profile, соответствующий `aps-environment`, регистрации токена и provider credentials того же Apple team/topic. При переподписи могут измениться bundle identifier, entitlements и environment. Заранее обещать APNs через любой общий сертификат Scarlet нельзя. Это инженерный вывод из требований APNs и разных способов подписи, а не утверждение о проверенной нами сборке.

Без подходящего APNs приложение работает и синхронизируется после открытия, но мгновенные фоновые уведомления не обещаются. Постоянный WebSocket в фоне не является допустимой архитектурной заменой push. Silent push также не считается гарантированной доставкой; принудительно закрытое приложение и системные ограничения проверяются отдельно.

## Два проверяемых режима поставки

- **Собственный корректный signing profile с push:** предпочтительная проверка полной функциональности. Backend хранит APNs token, topic и environment только для соответствующего устройства. Секрет APNs хранится вне репозитория.
- **Переподписанная IPA с ограниченными entitlements:** тестовая поставка с явно указанными возможностями. Если регистрации APNs нет, интерфейс сообщает об ограничении уведомлений; сервер хранит сообщения до обычного sync.

Публичную функциональную паритетность с Android нельзя объявлять, пока первый режим или эквивалентный реальный способ подписи не подтверждён на устройстве. TestFlight/другие способы распространения остаются возможной альтернативой по отдельному решению владельца.

## Проверка M0 на реальном iPhone

1. Собрать Release arm64 IPA с фиксированным bundle identifier. Зафиксировать версии Xcode/iOS и метод подписи.
2. Проверить embedded provisioning profile, signing identity и entitlements именно конечной установленной IPA после переподписи.
3. Установить через выбранный способ Scarlet, открыть, создать тестовый аккаунт и проверить key storage.
4. Получить реальный APNs token; отправить тест от нашего APNs provider с правильными topic/environment. Зафиксировать результат, не сам токен.
5. Повторить foreground, background, locked screen, энергосбережение, перезапуск телефона, принудительное закрытие приложения и повторное открытие.
6. Обновить IPA тем же bundle ID/team и убедиться, что локальная база и доступ к Keychain сохранились. Проверить отдельно смену team/profile: сохранность ключей не предполагать.
7. Проверить поведение при истечении/отзыве подписи и повторной установке без обещания, что старые ключи или sandbox сохранятся.

## Обновления и восстановление

Канал релизов выдаёт версию, changelog, минимальную версию iOS, хеш IPA и сведения о поддерживаемом signing-сценарии. Хеш подтверждает целостность скачивания, но сам по себе не удостоверяет издателя; для подлинности нужна подпись и доверенный канал.

Нельзя удалять приложение как универсальный способ обновления: это может удалить локальную историю. До переустановки пользователь получает понятное предупреждение о последствиях. Наличие recovery code восстанавливает учётную запись, но не потерянные ключи прошлой переписки.
