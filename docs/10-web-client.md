# Веб-клиент: подготовка к реализации

Статус: проектирование, 2026-10-19. Пользователь добавил веб-версию с общим дизайном Android. Сейчас изменены только макет и документы: приложение, зависимости, crypto worker и сервер не созданы и не установлены. План ниже задаёт будущую работу, не отчёт о готовых функциях.

## Предложенный стек

TypeScript + Vite, DOM/CSS, нативные browser API. UI-фреймворк, глобальный store, SSR и service worker на первом шаге не требуются. Это предложение ради небольшого начала, а не измеренное превосходство над фреймворками. Vite поддерживает vanilla TypeScript; Node используется только для сборки, backend остаётся Go. Основание: [официальный Vite guide](https://vite.dev/guide/).

Будущие области ответственности: UI, модель сообщений/черновиков, HTTP/sync, локальное хранилище, crypto worker. Общими с нативными клиентами остаются контракты и тест-векторы, а не их платформенные runtime. Целевые браузеры — актуальные стабильные Chromium, Firefox и Safari; точные минимумы фиксируются после проверки E2EE и API на M0.

Папка `apps/web/`, package manifest и lockfile создаются только при начале реализации. Сейчас их нет; команд сборки веб-приложения и CI пока тоже нет. Дизайн-HTML не следует объявлять production-клиентом или переносить целиком как готовую архитектуру.

## Барьер E2EE

Публичный веб-клиент шифрует сообщения и файлы на устройстве и использует тот же протокол, что Qt/Kotlin/Swift. Серверный шлюз расшифрования запрещён. До подтверждения криптоинтеграции допустим только явно обозначенный локальный UI с вымышленными данными.

У libsignal TypeScript-интерфейс связан с native Node add-on; npm-пакет поставляет нативные библиотеки. Из наличия TypeScript API не следует совместимость с браузером. Нужны проверенная браузерная реализация, лицензия и межплатформенные векторы; они ещё не выбраны. Основание: [libsignal README, Node/NPM](https://github.com/signalapp/libsignal#node).

Web Crypto предоставляет криптографические операции, но не заменяет выбранную реализацию messaging-протокола. Не писать собственный ratchet. IndexedDB является хранилищем записей, а не готовой зашифрованной БД; механизм защиты данных определяется отдельно. Основания: [Web Crypto](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API), [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API).

Предложение до M0 — веб как дополнительное устройство, подтверждённое основным нативным клиентом и входящее в лимит десяти устройств. Новая вкладка не создаёт новое устройство. Самостоятельная регистрация основного устройства из браузера требует отдельного решения о защите account identity.

## Ключи, сессии и несколько вкладок

- В localStorage допустима тема; токены, сообщения, приватные ключи и разблокированный ключ локального кэша туда не записываются. Защищённое хранение и повторная разблокировка ключа после перезагрузки — открытый вопрос M0, не готовая функция.
- В IndexedDB атомарно сохраняются зашифрованные crypto state и готовый ciphertext outbox. Удаление browser data трактуется как потеря локального устройства и истории; старый device ID не переиспользуется без ключей и подтверждения.
- У crypto state один владелец записи. На M0 проверить сериализацию отправки из двух вкладок, смену владельца после закрытия и сбой между шифрованием и commit. Web Locks — кандидат координации, не замена транзакциям: [документация](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).
- Предложение сессии: один origin UI/API, access token в памяти, refresh в Secure/HttpOnly/SameSite cookie. Нужны отдельные проверки Origin/CSRF и сохранение общей политики pending/approved устройств. Это ещё не финальный HTTP-контракт; нативные bearer-сессии сохраняются. Свойства cookie описаны в [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).

## Модель угроз браузера

XSS и подмена доставленного JavaScript могут дать доступ к разблокированной переписке. Non-extractable ключ не запрещает доверенному по origin коду использовать его; это не защита от вредоносного обновления UI. Следствие для проекта: HTTPS, строгая CSP, отсутствие сторонних скриптов/аналитики, отображение текста через безопасные DOM-операции, контролируемая поставка ресурсов. Эти меры снижают риск и не обещают защиту от скомпрометированного сервера раздачи кода. Основание: [W3C Web Crypto, security considerations](https://w3c.github.io/webcrypto/#security-considerations).

Нельзя обещать постоянную доставку закрытой или замороженной вкладке. При возврате обязательны sync и восстановление outbox; Web Push/PWA — отдельный этап после проверки браузеров. Основание: [Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).

## Следующие шаги после команды начать код

1. Зафиксировать ADR стека, лицензии и целевые браузеры. Создать минимальный `apps/web/` с точными версиями и lockfile; пока без сети и реальных аккаунтов.
2. Перенести согласованные токены и компоненты в проверяемый UI. Подтвердить клавиатуру, контраст, уменьшение движения и плотный fallback стекла.
3. Параллельно по плану M0 проверить браузерную криптобиблиотеку, локальные ключи и совместимость с нативными векторами. Без успешного результата не включать реальную переписку в публичную сборку.
4. После M0 подключить Go API: подтверждение устройства, send/sync, атомарный outbox и отзыв. Проверить дубли, offline, две вкладки, reload и смену identity.
5. Измерить [бюджеты](08-performance.md), проверить XSS/CSRF, сбой обновления, очистку хранилища и реальную доставку между всеми клиентами.

Установка SDK, запуск dev server, изменение VPS, DNS, SSH и публикация сейчас не выполняются. Текущая готовность — согласованный UI и документы для следующего этапа.
