# AGENTS.md

## Область и текущая стадия
- Правила действуют во всём NeoChat; более узкие правила добавляются только при необходимости.
- Сейчас есть проектные документы и интерактивный макет веб/Android, работающего мессенджера ещё нет. Не выдавать планы и целевые показатели за реализованные функции и измерения.
- Обсуждение и документация — по-русски; имена кода и API — по-английски.
- Перед изменением читать README.md и относящиеся к задаче документы из docs/.
- Для UI читать docs/05-interface.md, docs/11-motion-and-handoff.md и docs/design/tokens.json; сохранять согласованные переходы, поддержку reduced motion и доступность клавиатуры. Для передачи Claude есть CLAUDE.md.

## Думать перед реализацией
- Явно обозначать допущения, неопределённость и существенные альтернативы.
- При противоречивых требованиях назвать противоречие и запросить уточнение; независимую работу продолжать.
- Для многошаговой задачи дать короткий план с проверяемым результатом каждого шага.
- Предлагать более простой вариант, если он решает ту же задачу.

## Согласованные требования
- Desktop — Qt/C++; backend — Go; Android — Kotlin; iOS — нативный Swift и IPA для проверки через Scarlet.
- Веб-клиент включён в проектирование. Предложение — TypeScript + Vite без обязательного UI-фреймворка; зависимости и браузерная криптобиблиотека ещё не выбраны и не установлены. Перед реализацией читать docs/10-web-client.md.
- V1 включает личные чаты, файлы и небольшие группы; E2EE обязательно до публичного запуска.
- Отдельная VPN не является требованием. Не добавлять её как обязательную зависимость.
- Предложенные лимиты: 16 участников группы и 10 устройств аккаунта; менять вместе с контрактами и тестами.
- Не добавлять Electron, WebView для основного UI, микросервисы, Redis, Kafka или Kubernetes без конкретной потребности.

## Простота и точность изменений
- Писать минимум кода для поставленной задачи; без спекулятивных возможностей и абстракций на один случай.
- Менять только относящиеся к задаче строки, сохранять стиль существующего кода.
- Не исправлять соседний код и не удалять чужой мёртвый код; удалять только ставшие ненужными из-за своих изменений элементы.
- Не блокировать UI сетевыми запросами, БД или криптографией; использовать постраничные данные и ограниченные очереди.
- Не загружать всю историю чата или весь файл в память. У зависимостей проверять размер, поддержку и лицензию.

## Безопасность и протокол
- Не реализовывать криптопримитивы, ratchet или обмен ключами самостоятельно. Кандидат libsignal ещё требует M0 и лицензионного решения.
- Node bindings libsignal не считать браузерным SDK. До публичного веб-релиза обязательны совместимость E2EE с нативными клиентами, защита локальных ключей и проверка нескольких вкладок. Не расшифровывать сообщения на сервере ради браузера.
- Не добавлять plaintext fallback. Моки криптографии разрешены только в тестах и не входят в выпускаемые клиенты.
- Проверять права пользователя и устройства на каждом API; не доверять присланным user_id, membership и receipt.
- Идемпотентность, порядок commit/cursor, отзыв устройства и смена состава группы — инварианты из docs/03-protocol.md.
- Состояние криптосессии и готовый ciphertext outbox сохранять атомарно до отправки; при retry повторять сохранённый ciphertext.
- Не печатать .env, ключи, токены, тела сообщений, push-токены и парольные хеши в ответы, логи или тестовые снимки.
- Секреты и сертификаты не коммитить. Примеры используют вымышленные данные.
- Вне задачи не менять сервер, SSH, firewall, DNS или подпись приложений. Прежние разрешения пользователя учитывать.
- Текущая задача — дизайн и документация. Пользователь отменил установку инструментов; не устанавливать зависимости и SDK и не разворачивать сервисы без нового запроса.

## Проверка результата
- Ошибку воспроизводить значимым тестом, затем исправлять; рефакторинг проверять до и после.
- Для изменения поведения проверять соответствующий сценарий, включая ошибки и права доступа; не писать тесты, повторяющие реализацию.
- Для протокола обязательны проверки дублей, параллельных отправок, пропущенного ответа, удаления участника, отзыва устройства и обрыва sync.
- Для E2EE нужны совместимые межплатформенные векторы и проверка восстановления после сбоя записи состояния.
- После появления кода использовать реальные команды сборки и проверок из README соответствующего компонента; не выдумывать существующий CI.
- Размеры и скорость измерять на release-сборках по docs/08-performance.md; указывать устройство, версии и методику.
- В конце сообщать, что изменено, чем проверено и какие существенные ограничения остаются.
